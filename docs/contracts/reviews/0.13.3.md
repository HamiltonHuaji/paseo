## 已确认的兼容边界

用户明确选择：**旧端常规读取保持兼容；超大完整读取列为旧端已知限制，
新端修好分批完整读取后发行。**

v0.9.20 的实际 Node 客户端具有 100 MiB 单消息上限；本地真实 workerd relay
具有 32 MiB 单消息上限。L 的完整 JSON 响应约 128 MB，经原有加密和 base64 编码
约 170,540,128 字节，旧端单次完整请求不能通过这些上限。这不是服务器主动缩小
可读历史的许可：容量内的旧请求仍按原语义完成；新端完整读取不得截断或假报完成。
完整读取的调用语义保留，新 SDK 自动分批发送请求。

连接记录仍只有原 key 下的一份格式。当前版本保留不认识的记录和字段，按已理解的
编辑合并回同一份数据。没有额外旧格式副本；也没有修改已经发布的旧客户端。
旧端曾经删除的数据不能凭当前修复重新生成。

## 校验审计范围

审计追踪“解析失败或默认值 → 自动保存／迁移 → 删除或覆盖”的后果，而非把所有
schema 改宽松。覆盖 app 的共享存储及全部已发现调用方、Zustand 持久化 owner、
独立设置／草稿／技能计划 writer；desktop 的设置、身份、窗口、viewer 端口和附件；
server 的身份、agent／workspace／schedule／push／skill／Connected Hosts 数据、
Works／experiments SQLite JSON、任务 Markdown、worktree metadata、第三方 agent
配置；另检查 client、protocol、relay、plugins、website 与脚本的校验边界。

确认的破坏性行为包括整表删除、未知字段被 schema 投影后写回丢失、I/O 失败后重建
身份、未完成迁移触发清理、失败附件被过滤后清草稿，以及 union 宽松分支误吞整个
已识别对象。这些都有原失败场景及修复后的临时故障注入。
不删除数据与完全可编辑分别判定；保留但暂时不能使用的记录不记为完整通过。

## 安装和交叉兼容

最终包在 `/tmp` 下的独立 HOME、npm prefix、cache 与空配置中安装；没有 checkout
祖先目录，清除 `NODE_PATH`／`NODE_OPTIONS`，不借用工作区链接。
这次安装发现 bundled ACP SDK 的 peer dependency 会让 npm 成功退出却留下空的 zod
目录；打包现由外层发行包统一持有这些依赖，缺少必需 peer 时打包失败。
另修复安装目录位于旧 checkout 下时，CLI 错读祖先 checkout 版本的问题。
默认 npm 11 安装 293 个包成功，实际 CLI 报告 0.13.3，daemon 与 SDK 可启动。
`@getpaseo/server/client/protocol/relay` 均为 0.13.0-beta.1，真实路径位于该安装内；
zod 实际可加载，包内五个历史／传输关键模块与最终压力测试构建的哈希一致。
没有使用 `--legacy-peer-deps` 或 `--ignore-scripts` 绕过候选安装。

实际 v0.9.20 原始 tarball 的默认 npm 10／11 安装遇到相同的空依赖目录问题。
本轮旧端使用 `--legacy-peer-deps --ignore-scripts` 安装原包，再执行真实旧版客户端、
解码器与 daemon；没有修改旧端源码。旧版默认干净安装不记为通过。

新 CLI → 旧 daemon 的直连和 relay 共 13 项通过，包括 L 最近日志、attach、
完整分页与不存在会话／断连错误。完整读取为 113 页、22,501 条；直连 4.60 秒，
relay 26.04 秒，输出内容一致。最近日志／attach 首次有效输出为 0.67–0.91 秒。
完整日志按时间顺序输出，relay 首次正文为 25.92 秒；不把内部收到第一页当作 stdout。

最终安装的 CLI → 新 daemon：直连／relay 的 tail 和 attach 均只请求 50 条，
首次正文 0.580–0.814 秒；完整日志分别 6.258／27.999 秒结束，首次正文
6.119／27.860 秒，均为 113 页、22,501 条。同一 daemon 两条路径的输出一致；
跨新旧 daemon 的完整 stdout 存在下文列明的既有格式差异，不声称逐字节相同。
读取中断的实际安装 bin 在 0.617 秒以失败退出，没有输出成功或空历史；错误后
约 13 ms 即退出，原先未关闭 SDK 的延迟已消除。

实际 v0.9.20 CLI → 新 daemon 的 S 日志／attach 直连和 relay 四项成功，完整
15 条均可读取。旧 CLI 的一次 relay tail 在 0.908 秒取得正文、20.618 秒退出；
旧 CLI → 旧 daemon 的同样操作也在 1.017 秒取得正文、20.721 秒退出。
这是单列的旧端退出延迟观察，不把正文已取得写成进程已结束。

旧 daemon 的首次恢复仍可耗时约 643 秒；这是旧实现的性能缺口，不能用热读结果
宣称旧端冷恢复已修复。新 SDK 默认允许旧 host 的较长等待，明确超时选项仍生效。
本轮未验证 Windows 安装器／UI、真实 WAN、终端原生模块或所有 provider。

Node 26.3.0、npm 11.16.0、Codex 0.162.1；本机真实加密 relay。
系统文件页缓存未清空；每个冷例使用新的 daemon/provider reader，未预热历史。
L 是用户指定的 `2f624a7a-e35e-4a0d-bf93-5f217326f4e9` 副本。
