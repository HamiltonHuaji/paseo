# Fork 行为契约

这里定义 fork 交付后应有的行为。每次官方 baseline bump 都按这些契约逐项验收；
上游实现、fork 实现和重写后的实现适用同一标准。实现方案由当前代码结构决定。

## 编号与范围

模块中的每个编号都是独立核对项。沿用已有审计编号；新增要求使用新编号。
移动文档保留编号，拆分保留来源映射，退役保留决定和替代编号。
上游已经满足的行为仍保留验收编号，重复的 fork 补丁可以移除。

除特别标注外，条目属于本 fork 的行为要求；这不表示当前版本已全部满足。
“目标”表示用户提出、尚待交付的能力；“待决定”表示尚未批准的行为取舍。
初始缺口和静态风险见[升级验收记录](baseline-review.md)，不能用条目存在代替验证。

以下材料不构成新的实施要求：

- 用户已废弃的会话／状态存储设计，包括旧审计 `HISTORY-01`。其中的数据库、状态机和
  历史拆分方案不进入本契约；现有代码与具体 bug 的行为证据仍可用于验收。
- v1 的 Goal 管理、doctor/repair、post-turn reporting，云端 W&B 均不因出现在设计稿中成为本次 bump 的交付范围。VS Code 扩展已由用户于
  2026-10-22 明确退役，见 VSCODE-01。
- 多 daemon 会话迁移、远端工具执行和凭证共享仍属于后续分布式设计。这里的项目存储
  目标不承诺跨机迁移协议。
- 用户固定的 [viewer transport spec](../refactors/experiment-viewer-transport-spec.md)
  保留为独立目标；差距记录不能修改或视为已经满足该规格。用户于 2026-10-23
  明确保留已调优的 v0.9.20 Viewer，baseline bump 不实施传输替换，见 VIEWER-02/05。

已有要求的删除、降级或缩小适用范围需要用户的明确决定。实现途径的变化、上游等价
替代和修复实现中的缺陷不需要重新批准产品要求。

## AUDIT-01 — 每次升级都有完整的验收结论

升级记录能从旧产品提交、旧官方基线、目标官方 tag/SHA 和最终候选提交追溯到每项
契约及其证据。每项分别记录实现归属和验收结果；“上游已有”不是“已通过”。

旧 overlay 的提交与最终差异都有归属：产品要求、已被替代的实现、临时上游修复、
发行元数据或工具链维护。测试、依赖和格式变化按其作用记录，不伪装成独立功能。
本次遇到但尚未归类的用户修改也有记录，不会因重建分支而被丢弃。

已验证实现的性能与跨版本连续性属于迁移范围。目标规格、协议撞号或代码简化
不自动授权替换已调优的子系统；架构替换单独说明范围、代价与旧版对照证据。

验收：换一个 agent 或 checkout 后，仅凭仓库内的记录即可找到所有编号的结论、
未决项和证据；未验证项目不会变为通过，新增退化不会被记成既有缺口。

## DOCS-01 — 要求、实现状态和版本证据一致

长期要求与特定版本的观察分开维护。已发布的能力不再标为“尚未发布”；部分实现、
已知缺口、未来目标和废稿保持可辨认的状态。版本号和发布日期不能替代功能验收。

契约随日常维护更新，不等下一次 baseline bump。收到新的行为要求或回归报告时，
先映射已有编号；缺少约束则补正向结果与验收场景。缺陷记录关联契约和受影响版本，
修复记录填写实际证据与剩余缺口。登记 issue、补文档或提交修复均不自动代表验收通过。

验收：入口文档指向当前契约；旧审计与设计稿明确其范围，不能被后续 agent
误用为最新需求或已验收功能。文档、代码与报告冲突时，升级记录指出差异。
