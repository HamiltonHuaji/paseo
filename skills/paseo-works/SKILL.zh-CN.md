# Paseo works（中文翻译）

本文件是同目录 `SKILL.md` 的中文阅读版。Skill 名称为 `paseo-works`，加载入口仍为 `SKILL.md`。

## 简介

在开发或维护软件、执行训练与评估、处理数据、制作报告、图表、页面或素材时，通过 Paseo 记录工作进展、关联相关会话、组织产物。

此外，用户委托你将收集、分析或持续积累的材料与结果整理成可供查阅、使用的成果时，也应用本 skill。为产物安排明确归属和查看入口；存放位置已知或一次性交付都不排除使用。

按用户委托的目标判断：检索或分析仅为回答问题、提出建议服务时，不因此触发；用户委托整理材料或分析结果本身供其查阅、使用时，则适用。聊天创作和常规文件操作，不因产生了文件而触发。

查找或继续已有工作时也应用；后续工作仍归入原有主题或实验，具体记录按执行性质选择。无需等待用户要求记录，也不要求长期运行或跨会话。

## 执行指引

让用户能从 Paseo 找到工作及其成果。记录正在做的事，关联有用的会话，将产物随工作保存，并提供查看入口。把这些动作作为完成用户任务的一部分，无需用户维护工单或记住你把文件放在哪里。

使用 Works MCP 工具和[工具参考](references/tools.zh-CN.md)。如果当前 host 没有这些工具，继续用现有工具完成用户请求，并说明尚未登记的内容；不要编造调用、声称已经保存记录、直接修改数据库或挪用 v1 字段。v1 与 Works 的记录和入口各自独立。

## 开始前查找已有工作

根据项目和对话上下文查找相关记录与成果，修改前先读取相关记录。用户要找以前的结果时，返回已有入口和状态，不要重新生成一份。

后续工作仍归入已有主题或实验。Attempt 记录一次实验执行：新运行、重试、续跑都创建新 Attempt，即使延续同一个 W&B run。保留早先执行的输入、代码、起止时间和结果，便于独立理解与比较。

Issue 记录待解决的问题或要交付的变化。目标仍相同时，继续在该 Issue 中排障、实现和验证；一次编译失败或追加修改不要求新建 Issue。开发方案或执行需要独立保留结果、比较时，再另建 Item。用户调整需求时，更新当前请求。

选择用户在 Canvas 中能认出的领域或成果。软件修复放在所属模块或功能下，运行放在所属实验下，资料库、报告及其更新放在一起。开发中的具体工作用 Issue 记录，对应实验操作的 Attempt；不要给每个 Issue 再加一层 Attempt。同一开发 Issue 可以包含排障、实现、测试和整合。

Sessions 用于关联值得日后回来继续工作的会话。自动 touches 单独记录哪些 agent 实际执行过操作，不把每个参与者都变成长期关联。适合且获授权时复用熟悉该工作的会话，但不强制指定负责人。工作可以没有关联会话，也可以有一个或多个。会话关联不构成创建 agent、委派任务或打断其他会话的授权。

## 安排存储并隔离代码

生成材料前，获取所属工作的存储位置。尊重已有位置或用户指定的位置，并将其登记到工作记录中。不要把产物散放到任意目录，也不要把一次性脚本和配置放进可复用源码目录。需要保留的日志、报告、checkpoint 和页面放在可丢弃的代码工作副本之外。

并行修改代码时，使用独立的 Git worktree 和分支。同一次执行中的顺序修改与验证可以共享 worktree。开始执行时复用当前执行的工作副本，或从已知基线创建一个；排队工作和只读问题不需要。记录基线和预期整合目标。从 Paseo 获取对象的 storage 路径，用 Git 在其中创建 worktree；Paseo 不分配或管理这些 worktree。需保留的产物放在 worktree 子目录之外，不根据 v1 布局猜测 storage 路径。

让运行中的训练和验证使用不会被其他工作改动的代码。仅记录 commit 不能保护仍会变化的目录。尝试多个方案时，隔离各自的修改，保留足以比较结果的信息。

## 记录执行与进度

记录目的、相关输入与配置、代码版本、执行标识和输出位置。将结果关联到实际使用的代码。执行过程中更新进度和有意义的结果，包括失败与放弃的方案。让早先执行与后续重试、恢复保持可区分。

记录足以恢复工作或理解结果的信息，不必复制整段聊天或你的详细计划。不要仅为填充记录而增加探针、运行或检查。

额外的 JSON 配置放入 Config，例如作业 ID、输出位置、W&B ID 和超参数。记录已知的执行起止时间。updatedAt 自动反映已观察到的活动；反复读到不变的数据不能证明作业仍在推进。

对于长时间运行的工作，配置受支持的进度观测，使用户无需再找 agent 调查就能查看。标明正在运行的进程或作业，并记录如何观测其完成。尚未配置监测时，不要声称会持续监测。

## 交付可查看的成果

将需要保留的材料及其位置登记到所属工作中。提供集中的入口，供用户查看结果和相关材料。资料库的条目与索引放在一起；报告及其支撑结果通过报告入口访问。用户指定了输出路径，或交付物只有一个文件，都不省略这一步。

查看页面有助于检查结果时，创建 viewer。只挂载它需要的文件，将相关内容组织在同一入口下，不要为每个产物分别建页面。输出布局相同时可继承 viewer 配置。查看本地 W&B 时，挂载读取指标和 artifacts 所需的记录与内容，不假定一份 .wandb 文件包含全部数据。验证入口能打开预期结果。

汇报完成的内容、结果、查看入口和剩余工作。附加 Result 时，准确更新文字与 completed 状态；执行已结束也可以是失败或否定结果。完成不等于归档，也不自动完成所属模块、功能或其他仍在继续的工作。不要仅为了给每个 Item 显示完成复选框而附加 Result。

## 执行结束后释放 worktree

完成时，在用户授权范围内将选定修改整合到预期目标，并验证整合结果。放弃的方案也应先保留有用证据和需要恢复的代码，再释放 worktree。记录工作本身不构成 push、merge 或部署的授权。

暂停时，将需要保留的代码保存到可达的 Git ref 或受支持的快照中，包含未提交和未跟踪文件。记录恢复上下文后释放 worktree；继续时从保存的状态重建。清理后仍需使用的代码，应保留完整 commit 标识和使其可达的 ref。整合尚待批准时，将候选代码保存在独立于工作副本的位置。

删除 worktree 前，检查是否仍有进程使用它，以及需要保留的输出是否已妥善保存。不能为清理而丢弃未保存的工作或停止运行中的作业。安排后台作业完成后的清理，不要留给用户记住。有阻碍时报告具体原因。

不要仅因会话空闲或未来可能继续工作而保留 worktree。一个会话可以使用过多个工作副本；恢复时提供当前路径和基线。

## 工具操作顺序

1. 用 list_cards 查找已有 Card，读取相关记录，再限定在该 Card 内查询 Item。
2. 创建或更新合适的记录，在同一次回执里取得 storage 或所需组件。更新规则见[工具参考](references/tools.zh-CN.md)。
3. 将产物放入返回的 storage，或登记已有位置。用 Viewers 提供入口；需要在 Canvas 看曲线时，将 Metrics 直接附加到 Card。
4. 及时更新 Result。起止时间会自动填写；登记过去的执行时，提供已知的实际时间。释放 worktree 前保存有用结果。
5. 验证登记的入口，并将其放进交付说明。
